## 一、现状：哪条路准、哪条路不准

| 场景 | 计时来源 | 实测误差 |
|---|---|---|
| **观察者模式**（旁观位，`obs=1`） | 服务端倒计时（顶层 `bomb.countdown`，0.25 秒粒度） | **±0.07~0.3 秒**（4 局：−0.07 / +0.14 / +0.29 / −0.07） |
| 活着 + **自己下包**（T 方） | 锚点（安放触发包 − 0.10s） | **≈0**（5 局 CALIB 下界 +0.00~+0.02，全部"确定不早"） |
| 活着 + **看别人下包**（CT 方） | 锚点或常数补偿 1.0 | **±1 秒**，且**无从得知**（可反推的 11 局里 L_p 从 0.37 摆到 2.51 秒） |
| **死后观战（比赛里死了看队友）** | 同"活着"：GSI 一样只有迟到的安放事件 | **±1 秒**（⚠️ 2026-09-17 用户更正：这 **不是** 观察者模式） |

> ⚠️ **术语更正（2026-09-17 用户指出）**：**观察者模式**（旁观位）才有顶层 `bomb` 块与倒计时；
> **死后观战（看队友）收到的信息与活着时一样**。所以"死了就准"是错的 —— 对 CT 拆弹来说，
> 活着和死后看队友都受同一个 ±1 秒限制，这也正是音频方案要覆盖的两种状态。

第三行的误差**不是实现缺陷**，来源见第二节；它的表现就是用户说的"有过早也有过晚"。

## 二、关键问题：安放之后，GSI 里"一定会出现"的东西是什么？

用户原话："有没有什么 GSI 信息是一定在 C4 安放后会出现的（类似于滴滴声）"。
用**我们自己的 4802 个真实报文**统计（`runtime/c4timer.log` + `_archive/logs/`）：

| 判据 | 活着 / 死后看队友（`obs=0`） | **观察者模式**（`obs=1`） |
|---|---|---|
| `bomb=planted/planting` 的包 | 1255 | 1697 |
| 其中能拿到服务端倒计时（`exp=` 有值） | **0 / 1255** | **1697 / 1697** |
| 顶层 `bomb` 块（`bomb.state` / `countdown`） | 0 / 1255 | 2322 个包有 |
| `phase_countdowns` | 0 / 1255 | 2320 个包有 |

**结论：活着时，"安放"在 GSI 里只体现为一个字段 —— `round.bomb` 从空变成 `planted`**
（那一包的增量就是 `add:round.bomb=true`）。没有倒计时、没有顶层 bomb 块、没有
`phase_countdowns`，也没有 E2 已经证实的 `planting` 前兆状态（`planting` 从来不存在）。

而这个字段本身被 Valve **故意延迟**（2015-12-17 补丁原文："Bomb plant timer Game State
Integration event is now **slightly delayed** when playing on Terrorist or Counter-Terrorist team."），
实测延迟 **0.03~2.6 秒且随机**：同一晚 22:06 那局 2.51 秒、22:09 那局 0.49 秒，
而这两局在我们看到的报文里**长得一模一样**（上一包都是心跳、间隔里没有任何内容变化）。

⇒ **"滴滴声"式的第二个 GSI 信号不存在。** 想在"活着看别人下包"时更准，只能从 GSI 之外拿信息。

**一个例外（有价值）**：**自己下包**时，你自己的 `player` 块会变（C4 从背包里消失），
那一包不受上面那个延迟影响 —— 这就是"自己下包时锚点准"（5/5）的机制来源。
还需要一局 T 方的 `Δ`（变更键）数据最终确认（见 `实机反馈与待办.md` 第二十节）。

## 四、A 方案修正：**没有数字可读，但有更好的东西**（2026-09-16 晚，用户截图）

原 A 方案假设"游戏在 HUD 上显示 C4 剩余秒数，只是我们没读"。**用户实机截图推翻了它**：

- 正常时，HUD 顶部中央是**对局时间**（截图里是 `1:05`，下面 0:0 与人数）；
- **炸弹一安放，对局时间整个被换成一个红色 C4 图标**（周围有放射状短线 = 滴声的视觉化），
  **没有任何剩余秒数可读**。

⇒ "截屏 + 数字识别"这条路**不成立**，省下了原估的 2~4 个工作时段。
但这两张截图同时暴露出**更便宜也更准**的切入点：

### A′（新）：检测"红色 C4 图标出现"的那一瞬

| | 说明 |
|---|---|
| 做什么 | 只盯**对局时间那一个小方框**（位置固定），判断"原本是白色数字 / 现在变成红色图案"，取**翻转时刻** |
| 为什么准 | HUD 是客户端**拿到服务端权威状态后立刻画**的；Valve 那个 0.5~2.2 秒延迟**只发生在 GSI 这一层**，不发生在 HUD 上 ⇒ 图标出现时刻 ≈ **真实安放时刻**（差一个网络 tick，约 15~30 ms） |
| 精度 | **±0.05 秒**（一帧 16 ms 量级），而且正好覆盖现在最不准的场景：**活着看别人下包（CT）** |
| 为什么便宜 | **不需要 OCR、不需要学字模**：一个固定 ROI + 红色像素占比突变检测即可 |
| 代码量 | 约 **150~250 行**（采集 80~120 + 检测 50~80 + 接入状态机 60~100） |
| 工时 | 约 **0.5~1 个工作时段**（含一次阈值标定） |
| 可选加分 | 那圈"放射状短线"如果随滴声脉冲，还能量出**节奏**（越接近爆炸越急）作交叉校验——即 C 方案的**视觉版**，比听觉版稳得多 |

### 怎么验证它是对的（不用额外的真值）

日志已经会同时记录两条通道，**它们必须互相印证**：

- `GSI 揭示包时刻 − 图标出现时刻` 应落在我们实测过的那个延迟分布里（**0.03~2.6 秒**）；
- 如果两者差值**总是很小且几乎不变**，说明我们测到的不是 HUD 延迟而是别的东西（要查）；
- 观战时分（有服务端倒计时真值）还能做绝对校验 ✓

### A′ 的成本与风险（如实）

- **运行成本**：每秒几次、只截一个小方框 ⇒ 可忽略（实测后给数字）。
- **维护成本（真正要付的）**：分辨率或 HUD 缩放变了 ⇒ ROI 要重标（一张截图即可，可做成自动找框）；
  计分板等遮挡 ⇒ 那几帧跳过；**独占全屏**可能截不到 ⇒ 需实测（退路：游戏内切无边框全屏，安全）；
  游戏大更新改 HUD ⇒ 可能要重标。
- **兜底原则（同 B）**：**检测不到就退回现有估算**，绝不因为屏幕识别失效而让面板变差。
- **仍待确认**：① T 方是否也显示这个红图案（决定覆盖范围）；② 图标是不是"一安放就出现"
  （用上面那条互证来确认）；③ 你的全屏模式。

## 五、B 方案细化：听**安放播报语音**（2026-09-16 晚，用户指定）

用户原话："能不能用声音检测？**只有作为 CT 方时才需要这个**。GSI 信息会有延迟，
但炸弹安放后的**语音播报没有**。" —— 这个判断是对的，理由如下。

### 为什么播报语音是对的目标（而不是滴声）

| | 滴声（C4 beep） | **安放播报语音** |
|---|---|---|
| 形态 | 周期性重复，整局都在 | **一次性事件**，只有安放那一刻 |
| 与别的信号混淆 | 与"拆弹声"同属 C4 电子音 ⇒ 当年就是卡在这里（真身 0.821 对误报 0.769~0.802） | 是**固定的一句播报**，与其他播报（"炸弹已拆除"等）在音频上可区分 |
| 适合的算法 | 需要"节奏"这类弱特征 | **匹配滤波（已知信号检测）**：模板就是那一声，信噪比要求最低 |

**时机上为什么不吃 GSI 那个延迟**：播报由客户端自己的游戏状态触发（客户端在收到服务端
状态时**立刻**就播），而 Valve 那 0.5~2.2 秒延迟**只发生在 GSI 这一层** ⇒ 播报时刻 ≈
真实安放时刻（差一个网络 tick + 音频调度，几十毫秒）。与 A′（HUD 红图标）同一个道理，
只是换了一个感官通道。

### 归档里已有的家底（这才是成本低的原因）

`_archive/audio_removed_20260916/` 里有整套东西，其中最关键的是
`_archive/audio_removed_20260916/tools/capture_session.py`（现行版本是
`tools/record_audio.py`）：**一边 WASAPI 环回录音（单声道 16bit 48kHz），一边收 GSI，
两者样本级对齐**（音频线程累加帧号 `total_frames`，GSI 回调把 `(recv_mono, total_frames)`
一起写盘 ⇒ 任何 GSI 事件都能换算成 WAV 里的精确样本位置，误差 ≤ 一个音频块 ≈10ms）。

也就是说：**标定工具不用重写**——录一局就有了"音频 + 精确事件时间"的数据，
"安放播报到底长什么样、在枪声里能不能听见"这个问题当场就能回答。

### 录制方式与已完成的准备（2026-09-16 晚）

**用户新增的三条要求（已据此定稿）**：

1. **只在 CT 方需要，且不分存活与否** —— 活着时用实时音频流；**死后观战（看队友）也一样启用**。
   ⚠️ 更正（2026-09-17 用户指出）：死后观战**不是**观察者模式，它拿到的信息与活着相同
   （没有服务端倒计时）⇒ 所以它和活着一样需要音频；只有真正的**观察者模式**（旁观位）
   才有服务端倒计时，那时音频只当交叉校验。
   ⚠️ **再更正（2026-09-19，阵营门控已取消）**：这一条原来是"只在 CT 方"，理由是
   "T 方自己下包本来就准"。用户实机复核发现那只覆盖了**自己下包**：**T 方队友下包时，
   变的是队友的背包，你自己那一包数据没有任何变化**（`allplayers` 是观察者组件，
   活着时根本收不到），锚点同样要退到常数补偿、同样有 ±1 秒误差。
   ⇒ 现在**两队都启用**。自己下包那种局锚点准到 0.02 秒，由
   `state.AUDIO_KEEP_ANCHOR_SEC`（音频与锚点差 < 0.3 秒就不动 T0）保住，不被覆盖。
2. **模板要中英文都有** —— 用户可提供中英文录音（改游戏语言各录一局即可）。
   检测器按"多模板并行匹配、取最高分"设计；哪几种模板有效**从录音里自动判定**。
3. **视觉方案（A′）暂缓**，先做声音。

**归档链路已搬回并跑通（主程序一行未改）**：

- `tools/record_audio.py` 从归档搬回（现在直接 import 产品的 `c4timer.audio`，
  不再需要当年那个 `tools/c4audio/` 过渡目录 —— 它只存在于 2026-09-17 的中间状态，
  早已删除），只做了 import 适配；采集所需的 4 个字段现在由产品配置
  `c4timer/config.py` 的 `AudioConfig` 提供。
- 一键录制：仓库根目录 **`录音一局.bat`**（纯 ASCII + CRLF，与现有启动器同规矩）。
- **已实测**：48kHz 单声道 16bit WAV、无报错（3.07 秒 / 147360 样本，RMS=0 因为当时没声音在播）；
  设备枚举正常（默认"扬声器 (High Definition Audio Device)"）。
- **额外的好消息**：它优先使用**进程环回**（归档日志里
  `no process matching ('cs2.exe'); using system loopback`）—— 即游戏一开，**只录 CS2 自己的声音**，
  Discord / 音乐 / 其它程序的声音进不来；CS2 没开时才退回系统环回。这直接消掉了"别的程序干扰"这一类误报。

**录的时候请这样做**（每一条都影响标定质量）：

1. **先关掉 c4timer 悬浮窗**——它占着 GSI 端口 30077，两个程序不能同时听同一个端口。
2. **中文客户端录一局**；再把 CS2 语言切成英文，**英文客户端录一局**（模板两种都要）。
3. 正常打：要有**多次安放**、**枪声**（用来量漏检）。（死了看队友**不是**观察者模式，
   拿不到服务端倒计时；只有进旁观位才有——所以别指望靠"死一次"来标注真值。）
4. 打完回到窗口按 **Ctrl+C**，然后把打印出来的 `sessions\session_YYYYmmdd_HHMMSS` 目录告诉我。
   （`sessions/` 在 `.gitignore` 里，录音不会被提交。）

### ✅ 可行性已验证（2026-09-17 00:08 那份录音，366.66 秒 / 3 次安放）

用户用耳朵报出三段播报的大致位置后，定向对齐 + 模板匹配的结果：

| 项目 | 结果 |
|---|---|
| 三次播报的对齐 | 相似度 **0.719 / 0.662**（相对基准），**留一法交叉验证 0.721 / 0.754 / 0.706** |
| 播报起点 vs GSI 揭示包 | 早 **0.34s / 2.40s / 0.92s** —— 正好落在实测的 GSI 延迟区间（0.03~2.6s）内 ✓ |
| 整段扫描（除 3 次安放外全是误报考查区） | 阈值 0.60 → 3/3 命中、9 处误报；0.65 → 3/3、4 处；**0.70 → 3/3、1 处**（且那一处在**主菜单**里） |
| 判别裕度 | 真身得分 **0.86 / 0.86 / 0.83**，其他播报（回合胜负/拆弹成功）最高 **0.70** ⇒ 阈值 ~0.78 可全分 |

⇒ **"听播报"这条路技术上成立**，而且拿到的就是真实安放时刻（比 GSI 早 0.3~2.4 秒）。

**设计要点（延迟与精度兼顾）**：

1. **两段式**：先用**开头的 0.3~0.5 秒**做"快触发"（延迟 ≤0.5 秒，让面板尽快出现），
   再用**完整 2 秒模板**确认，并把 T0 **回溯修正**到精确起点（误差 ±0.05 秒）——
   面板上表现为一次极小的平滑校正，用户看不到跳变。
2. **门控**：只在"你在 CT 方 + 回合 live + 还没收到 GSI 揭示包"时跑（顺带把主菜单里的
   那次误报排除掉）。
3. **多模板**：中英文各一套（用户会分别录），匹配时取最高分；模板从**用户自己的录音**里
   自动切出来（`plant_voice_template.npy/.wav` 落在 `sessions/` 下，**不进版本库**，
   避免把游戏音频提交进仓库）。
4. **兜底不变**：检测不到就退回现有估算。

**还需要的数据**：英文客户端录一局（第二套模板），以及再一局中文录音（把阈值定死、
把误报率量准）。目前只有 3 个正样本，阈值先按 0.78 试。

### 风险（如实，全部有兜底）

1. **枪声/队友语音盖住播报 ⇒ 漏检**：漏了就用现有估算，**不会比现在更差**（当年"爆炸声检测"
   实机一次没响过，所以绝不能把音频当唯一来源）。
2. **语音包/语言必须是自己的**：中文客户端播报是中文，模板只能从**你自己的录音**里建，
   不能拿别人的。
3. **系统音量太小 ⇒ 信噪比差**：建议保持游戏默认音量（我们会检测"录到的电平恒为 0"并提示）。
4. **耳机/扬声器都行**：WASAPI 环回录的是**播放设备**的输出，和插不插耳机无关。
5. **虚拟声卡/音频增强**（Voicemeeter 之类）会改变链路 ⇒ 需实测。
6. **CT-only 门控**：按你说的只在 CT 方启用，占空比低、误报影响面小；自己下包的局本来就靠锚点
   （5/5 精确），不需要它。
7. **安全**：环回录音是被动采集，和 OBS 录音同类，不碰游戏进程。
