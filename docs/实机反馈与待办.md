## 一、当前形态（决定清单，全部已拍板）

| 项 | 决定 |
|---|---|
| 显示什么 | 一行红字：**炸弹时限**（= 游戏自己那个 40 秒计时器归零的时刻，也是"拆弹的最后时限"） |
| 语义 | 归零 ≠ 真爆；**真爆比它晚约 1.05 秒**（实测，见第四节） |
| 精度 | 剩余 >15 秒显示整数（**向上取整**，口径 = 游戏「还剩第几秒」，见第十节）；最后 15 秒一位小数 |
| 时限已到、还没爆 | 数字变灰停在 `0.0`，状态行写 **「时限已到 · 即将爆炸」** |
| 真爆 | `0.0` + 「炸弹已爆炸」→ 1.5 秒后消失 |
| 拆弹成功 | 红字停住 + 「拆弹成功」→ 1.5 秒后消失（GSI 驱动，不需要音频） |
| 40 秒内回合结束 | **重置**（`round.phase` 变 over/freezetime、`map_round` 变化都算） |
| 中途启动/重连、没看到安放 | 显示 **「时限未知」**（观战拿到真值则正常显示） |
| GSI 断连 | 保留断连提示 |
| 估算值标记 | **不标**（用户决定；风险写在 README 的「已知边界」里） |
| 最后几秒加强提示 | 不加 |
| 补偿值维护 | 手调常量 + 日志复核；**不做**运行时自适应 |
| 拆弹绿字 | 已移除（用户明确不要） |
| **回合刚开就安放好**（我们晚 4~5 秒才看到） | **不特殊处理**（用户拍板）。实测 57 次 `freezetime→live` 切换里有 9 次是"切换后第一包就已经是 planted"（间隔 4.3~5.5 秒），这些回合红字会**系统性偏晚最多 ~5 秒**。不改成"时限未知"、也不用"安放动画 3.2 秒"去估 —— 若实打起来发现影响判断再议。 |

## 二、为什么活着时的红字天生有秒级误差 —— Valve 是故意的

**官方**（CS:GO 2015-12-17 补丁说明，`[GAME STATE INTEGRATION]` 一节）：

> "Bomb plant timer Game State Integration event is now **slightly delayed**
> when playing on Terrorist or Counter-Terrorist team."
> —— <https://blog.counter-strike.net/2015/12/13409/>

**社区**（两个独立库把同一次改动描述成随机延迟）：cs-gamestate、GoTimer 的 README
都写着 "bomb planted event is now **randomly delayed**"。

**本机实测**：

| 信号 | 延迟 |
|---|---|
| 观战 `bomb.state = exploded` | **0.07~0.08 秒**（用录音里"急促滴声转连续轰鸣"的起振点标定） |
| 活着 `round.phase → over` / `round.bomb → exploded` | ≈ 0.04 秒 |
| **活着 `round.bomb = planted`** | **0.5~2.2 秒**（可信样本 1.84 / 1.94 / 2.00 / 2.10 / 2.17） |

结论：慢的**不是 HTTP 通道**（同一条通道的爆炸通知只要 0.07 秒），也不是发包节奏
（安放延迟与"前一包距今多久"**不相关**，r = −0.26）。慢在**游戏内部把 `round.bomb`
置成 `planted` 的那一刻**本身 —— 而且这是有意的，目的就是不让计时器类工具好过。

所以：
- **cfg 调参救不了它**（`buffer` 的语义是"最多压 0.1 秒再发"、`throttle` 是"最小发送间隔"）。
- 想拿到亚秒级红字，只有一条路：**死着观战**（服务端 `bomb.countdown`，0.25 秒粒度）。

## 三、E1 实验：把 `buffer`/`throttle` 从 0.10 降到 0.02 —— **结论：没有明显改善**

改之后**发包确实变密了**（出现过一个 **0.071 秒**的报文间隔；`throttle=0.10` 不可能
产生小于 0.1 秒的间隔，所以新 cfg 确实生效了）。但安放延迟本身没下来：

| | L_p 样本（秒） | 中位 |
|---|---|---|
| 改节流**前**（可信样本） | 1.84 / 1.94 / 2.00 / 2.10 / 2.17 | 1.95 |
| 改节流**后**（两条链夹出来的估计） | 1.14 / 1.22 / 1.52 / 1.62 / 1.87 / 2.35 | 1.57 |

差别（0.4 秒）落在噪声里，**所以补偿值维持 1.85**（合并 11 个样本后中位仍≈1.85）。

⚠️ **一处自我更正**：改节流后第一局出现过一个 **0.44 秒**的样本，我当时据此判断
"可能找到了可调的开关"。样本变多以后看清楚了：那只是一局"宣布安放那包的前一包
刚好离得很近"，属于同分布的偶然小值 —— 改前也有过 0.54 秒的弱样本。
**教训：n=1 的"反例"不能当机制证据。**

### 夹层法是怎么估 L_p 的（免得以后看不懂）

- 链 A（爆炸侧，来自 `CALIB`）：`L_p ∈ [comp + calib_lo, comp + calib_hi]`
- 链 B（安放报文侧，**不依赖任何常数**）：`L_p < gap_prev`（安放必然发生在
  "宣布安放那包之前的一包"之后）
- 两条链常常相差约 0.1 秒（链 A 下界略高于链 B 上界）。冲突时真值就夹在两者之间，
  取夹层中点；实测这个中点的误差约 ±0.1 秒。

## 四、"1.05 秒"是怎么来的 —— 而且**已经用 4 局观战数据验证过了**

唯一一局同时看得到服务端倒计时的（19:07）：

```
19:07:02.214  GSI  exp=32.6 obs=1     -> 倒计时归零 = 19:07:34.814
19:07:34.844  STATE armed -> exploded   （我们的本地归零，差 30ms）
19:07:34.930  GSI  bomb=planted         （这一包炸弹还没爆）
19:07:35.931  GSI  phase=over bomb=exploded
```

→ **倒计时归零到真正爆炸之间隔了约 1.05 秒**。外部旁证：社区资料里描述 C4 倒计时末尾
"额外的 1 秒（白灯）"。这条决定了 `explode_after_deadline_sec = 1.05`。

**验证（第二份日志，4 局你死着观战看到的爆炸）**：观战时本地归零直接由服务端倒计时给出
（= 截止时刻），所以 `CALIB` 的误差就是"两个常量准不准"的直接读数：

| 局 | 误差区间 | 中点 |
|---|---|---|
| 22:46:39 | [−0.07, −0.07] | −0.07 |
| 23:22:10 | [+0.14, +0.14] | +0.14 |
| 23:31:38 | [+0.10, +0.48] | +0.29 |
| 23:35:36 | [−0.07, −0.06] | −0.07 |

**均值 +0.07 秒** —— 说明 1.05 秒这个常量在实机上是对的（±0.1 秒内），
观战路径的对齐也是准的（两局的区间宽度只有 0.01 秒，说明爆炸报文是即时的）。
那个 ~0.1 秒的系统偏差（见下）在这里表现为 +0.07。

顺带发现一个 ~0.10 秒的系统偏差：两条**互相独立**的证据链（爆炸通知侧 vs 安放报文侧）
在 15 局里有 13 局不相交，差值近乎常数（中位 +0.101 秒）；那个不依赖任何常数的真值锚点局
也超出上界 +0.095 秒。指向"`0.07+1.05` 整体偏小约 0.1 秒"或"GSI 数据本身有 0.1 秒滞后"。
对红字的影响是 0.1 秒量级，**远小于活着时那 ±1 秒以上的随机量**，暂不追。

## 五、`CALIB` 日志：每局爆炸时自报误差区间

```
CALIB  本局误差 [-0.00, +0.18]s  T0来源=gsi+comp  当前补偿=1.85  建议=1.94
CALIB  本局误差 [-1.74, +0.80]s  T0来源=gsi+comp  当前补偿=1.85  区间太宽（报文间隔 2.61s），不给建议
```

- 误差 = 本地归零 − **截止时刻**（参照系跟着红字语义走）。
- 给的是**区间**，不是点估计：真实爆炸必然落在"上一个报文"和"报爆炸那个报文"之间。
- 区间宽于 0.3 秒就明说"这一局证明不了什么"，不给建议值。
  这一条是被教训换来的：第一版给点估计，7 局全报"偏快"（−0.03 ~ −1.76），
  差点据此把补偿值改成负数；后来发现那些局的报文间隔是 0.9~9 秒，**什么都说明不了**。
- 可靠样本很稀疏（40 局里只有 2 局区间窄于 0.3 秒），所以"靠日志调参"要慢慢攒。

## 六、为什么砍掉绿字（留个交代）

实机反馈里的现象与根因：

| 现象 | 根因 |
|---|---|
| 绿字漏报多 | **实机环境的分数是稀疏尖峰**（每两三秒冒一帧 ≥0.75），而标定会话里真拆是**连续 0.87~1.00 整整 10 秒** —— 模板/阈值是在另一个声学环境下标定的（音量/耳机/地图/远处拆弹） |
| 假拆识别不出来 | 旧规则只看"距最后一帧达标多久"，会被稀疏尖峰一直续上，静默规则永远不触发（新一局 6 次假拆全卡在 10 秒判定窗） |
| 队友拆、旁观拆没有绿字 | 活着时 GSI **完全不给**拆弹信息；远处的拆弹声本来就听不到 —— 这是硬边界 |
| 有误报 | 只响一下的误报会挂在屏幕上直到 10 秒判定窗关闭 |
| 读秒一卡一卡 | ①音频线程把 ticker 挤到 47ms（已用"频带求和矩阵"向量化，从 5 次/3 秒降到 3 次/3 秒）；②同一段拆弹被不应期每 2 秒重复检出、每次都重新计时 → 绿字往回跳 |

结论：**这条路的判别余量太薄，投入产出比不划算**，用户明确不要了。
完整实验记录（含 552 秒真实会话的留一法验证、36 组阈值扫描）归档在
`_archive/音频可行性实测.md`。

## 八、教训（写给未来的自己）

1. **"看到了峰值"不等于"判据成立"。** 诊断指标要挑直接对应判据本身的量（这里是达标帧数/密度），
   别拿一个容易满足的旁证当证据。
2. **别把"区间中点"当估计值。** 宽区间只能证否，不能证实。
3. **改默认值之前先确认没有 `config.json` 把它钉住**（踩过）；
   而且 `config.json` 带 BOM 会让整份配置被**静默忽略**（也踩过，现在能读 BOM 且会报警）。
4. **方向性错误代价极大**：补偿值"越大归零越早"这个方向曾经推反。
   所以每个方向性常量旁边都写了方向。
5. **不要自己给自己写"看起来有效"的结论**：E1 我原本判断"收益基本为零"，
   是用户坚持做了才拿到那个 0.44 秒的样本。

## 九、E2 实测：那 2 秒延迟到底发生在哪一层（2026-09-15 晚）

数据：`runtime/c4timer.log`（19:01~23:38，2141 条 GSI 报文，10 次启动；
**23:16 之后**是当前版本 = 补偿 1.85、拆弹声判定已删）。
分析脚本：`_archive/analysis/e2_plant_timing.py`、`_archive/analysis/lp_from_fixture.py`（都是只读、可重跑）。

### 9.1 `planting` 不存在 —— 原来的假设作废

2141 条报文里顶层 `bomb.state` 只出现过 **planted / defusing / exploded**；
`planting`、`carried`、`dropped` **一次都没有**。所以"我们在等 `planting → planted` 那一跳"
这个猜想是错的，**没有更早的信号可以抢**。

### 9.2 顶层 `bomb` 组件（含游戏自己的倒计时）只在"观察者组件可用"时才有

| | planted 报文数 | 其中带 `exp`（倒计时）的 |
|---|---|---|
| 活着（obs=0） | 475 | **0** |
| 观战（obs=1） | 899 | **899** |

`obs` 这个字段的真身是"载荷里有没有顶层 `bomb` 键"（`gsi.py: OBSERVER_KEY = "bomb"`）。
夹具侧独立验证：有 `bomb` 键的 103 个包**全部**满足 `player.steamid != provider.steamid`
（在看别人），而 `player.steamid == provider.steamid`（自己）的 90 个包一个都没有 `bomb` 键。
→ **活着时拿不到服务端倒计时是硬边界**，不是我们解析漏了。

### 9.3 观战那一路**没有**延迟

6 次观战安放的**第一包**就已经是 `planted`，且带着游戏自己的倒计时（下表 5 次，
第 6 次是 23:35:20.748 的 `defusing → planted` 回落 —— 拆弹中断，不算安放）：

| 时刻 | exp | δ = 40 − exp | 距上一包 |
|---|---|---|---|
| 22:46:51.089 | 39.90 | 0.10s | 0.12s |
| 23:18:50.012 | 40.00 | 0.00s | 0.09s |
| 23:21:29.027 | 40.00 | 0.00s | 0.06s |
| 23:30:57.945 | 40.00 | 0.00s | 0.08s |
| 23:34:55.759 | 39.90 | 0.10s | 0.07s |

而且这个倒计时是**活的**：相邻观战包 `Δexp/Δt` 中位 **0.971**（≈1.0）。
它的归零点与游戏报 `exploded` 的时刻相差 1.05 秒 —— 23:34:55 那局：
倒数到 0.0 在 23:35:35.706，`exploded` 报文在 23:35:36.752（+1.046s）✓ 与
`explode_after_deadline_sec` 完全吻合。**观战路径既准又即时，2 秒不是它的问题。**

### 9.4 活着那一路：没有倒计时 + 包稀疏

| | 报文间隔中位 | p90 | 最大 |
|---|---|---|---|
| 观战（obs=1） | **0.09s** | 0.11s | 3.03s |
| 活着（obs=0） | **1.83s** | 10.04s | 10.52s |

活着时我们只能在收到 `round.bomb=planted` 那**一包**开始自己的 40 秒。
"安放包距上一包"的间隔（= 我们晚到的**上界**）在 **58** 个活着样本里是
**0.09~6.10 秒、中位 1.62 秒、均值 1.71 秒、p90 2.48 秒**。→ 2 秒延迟 = **Valve 故意延迟 +
活着时的发包节奏**，不是某一层"卡住"了。也正因如此，单一个常数补偿不可能每局都准
（这正是 `CALIB` 只给区间的原因）。

### 9.5 L_p 的**直接**测量方法（新）—— 夹具上量到 0.92 / 1.41 秒

E2 让这件事第一次变得可测：**同一回合里先活着挨到 `planted`，之后又死着观战拿到倒计时**，
就能反推真实安放时刻：

```
t_plant = t_观战包 − (40 − exp)          # 倒计时已证明是活的
L_p     = t_活着看到 planted − t_plant
```

夹具 `fixtures/gsi_capture_20260915.jsonl` 上有 2 个这样的回合：

| 回合 | 活着看到 planted | 反推真实安放 | L_p | 倒推一致性 |
|---|---|---|---|---|
| r=1 | 13:09:37.822 | 13:09:36.90 | **+0.92s** | −0.06s |
| r=1 | 13:28:41.618 | 13:28:40.21 | **+1.41s** | +0.01s |

## 十、"倒计时比实际快 1 秒"（2026-09-16 实机反馈）—— 是取整口径，已改成向上取整

**反馈原话**：倒计时比实际快，**差得差不多固定 1 秒**，**活着和观战都见过**，
对照的是"拆弹的最后时限"。

**先排除"钟走快了"**：观战那一路的钟是**锁死在服务端倒计时**上的
（同时刻的 `CALIB` 误差只有 ±0.07 秒，见第四节 4 局验证），
所以那 1 秒**不可能是计时误差**，只可能是**数字被印低了**。

**定位**：`render._fmt` 当时是 `int(value)` = **向下取整**。

| 真实剩余 | 游戏 C4 数字（"还剩第几秒"= ceil） | 旧版红字（floor） |
|---|---|---|
| 39.9 | 40 | 39 |
| 20.0 | 20 | 20 |
| 19.9 | 20 | **19** |
| 15.9 | 16 | **15** |

→ 整段倒数**永远差 1**，活着/观战都一样（这就是"固定 1 秒 + 两种状态"的来源）；
而且在整数档里"显示 0 的那一秒"也提前了一秒。

**修法（已实施）**：整数档改成 `math.ceil(value - 1e-9)`（口径 = "还剩第几秒"），
`render.py` 里写了原因；显示层自检 63 → 64 条（新增 `39.9 -> 40` 一条），
整套自检 **全绿**。最后 15 秒仍然是一位小数（比游戏的整数更细，这是刻意要的精度）。

**如果还是差 1 秒**，那就只剩另一种解释需要你确认：
**红字归零（灰 0.0「时限已到」）的那一刻，游戏里的 C4 数字显示的是 0 还是 1？**
- 显示 **0** → 我们的零点和游戏一致，上面这条就是全部问题，已修完。
- 显示 **1** → 说明游戏那个数字的零点是**真爆**而不是"计时器归零"，
  也就是说"拆弹的最后时限"其实等于真爆那一刻（比我们的零晚 1.05 秒）。
  那就不是取整问题，而是**零点口径**问题 —— 改法是 `render`/`state` 里
  把红字零点整体后移 `explode_after_deadline_sec`（1.05 秒），一句话我就能改。

**次要来源（活着那一路）**：补偿值 1.85 是"典型值"，逐局真实 L_p 在 1.2~2.4 秒之间
（第九节 §9.5 夹具上直接量到 0.92 / 1.41 秒），所以活着时还会剩下 **±0.6 秒左右**的抖动 ——
那是 Valve 故意延迟造成的，消不掉；若修完取整后仍嫌偏快，可以把补偿从 1.85 降到 ~1.4
（要先用当前 cfg 再攒几个直接测量的样本）。

### 10.1 追加反馈："安放后直接从 38 秒开始计时"

即：**早 1 秒是安全的、晚 1 秒是致命的**。所以除非你要的是"看着好看"，零点半点都不要往后挪。

## 十三、日志为什么一个字都不长：**文件被设成了只读**（2026-09-16 02:1x 查明）

**现象**：用户连着报了三轮实机观感，而 `runtime/c4timer.log` 一直停在 23:38、一个字节没长。
我据此判断"程序没在跑"—— **这个判断是错的**。

**真因**：那个文件被加上了 Windows **只读属性**。

```
Get-Item runtime\c4timer.log | Select Attributes   ->  ReadOnly, Archive
p.open('a')                                        ->  PermissionError(13, 'Permission denied')
SessionLog(...).enabled / .error                   ->  False / PermissionError(13)
```

`SessionLog.__init__` 捕获 OSError 之后**静默**把日志关掉（`enabled=False`，`error` 只存在内存里、
从没打给用户看）→ 程序照常收 GSI、照常显示面板，**只是不写日志**。
所以"面板正常、日志是空的"这个组合是可能的 —— 我上一轮把它读成了"程序没启动"。
（`_bg_ingame.png` 也是只读的，可能是为了保住 E2 那局的证据时一起设的。）

**改了三处**（自检 362 全绿）：

| 改动 | 目的 |
|---|---|
| `SessionLog._open()`：遇到 `PermissionError` 先 `os.chmod(path, S_IWRITE)` **清掉只读再开一次** | 属性问题不该让证据链断掉 |
| 仍失败时把 `error` 记下来，并且 `run()` 启动时**打到控制台**（`[!] 日志没开：…`） | 再也不会"静默" |
| 启动横幅 `START`（日志第一行）+ 控制台打印 `日志: <路径>` | 一眼回答"跑没跑、参数是什么、日志在哪" |

**教训（写进第八节同级的规矩）**：**"没有新日志" ≠ "程序没跑"**。
判断"跑没跑"要分别查：端口是否 LISTENING、有没有 python 进程、日志文件的**属性**与 `error`；
只看"文件没长"会得出完全相反的结论（这次就误判了一轮）。

## 十六、继续压缩活着那一路的误差（2026-09-16）

### 16.1 先更正一条旧结论：L_p **确实**与包间隔有关

旧笔记（第二节 / README）写的是"L_p 与包间隔**不相关**（r = −0.26）"，
那是拿**宽区间的中点**算的 —— 而宽区间的中点本身没有意义（第四节教训 2）。
换成可靠的点估计（`CALIB` 下界：因为爆炸通知只要 0.07 秒，下界≈点估计）重算，
17 局全部满足：

```
L_p ≈ (报安放那一包 − 上一包) + 0.11s        等价于   T ≈ 上一包时刻 − 0.11s
```

夹具里那两局（用**完全不同的方法**测：观战倒计时反推真实安放）给 L_p = 0.92 / 1.41，
而"间隔 + 0.11"给 1.00 / 1.47 —— 差 0.06~0.08 秒，在已知系统偏差的量级内 ✓。

**机制猜想**：Valve 延迟的不是"发包"，而是把 `planted` 这个**状态**藏起来 ——
安放后约 0.11 秒游戏确实发了一包（被安放事件触发），但那包的炸弹状态还是旧的；
带 `added: {"round": {"bomb": true}}` 的包要等**下一次**发包机会。
所以"安放前最后一包"的时刻，才是离真实安放最近的时间戳。
夹具里 6/6 个安放跳变的上一包都带内容变化（`added`/`previously` 非空）✓。

## 二十、"变化键"诊断：锚点能不能从**内容**上认出来（2026-09-16 晚加，待实机取证）

**为什么做**：第十九节之后，活着那一路的残余误差是 ±1 秒级的"结构性抖动"——根子在于
"哪一包是被安放事件触发的那一包"**只能靠间隔猜**（`chg=1` 且间隔 ≤3 秒）。Valve 的增量提示
`previously`/`added` 里带着**改了哪些键**，如果"安放触发包"在内容上可识别，就能把它认出来、
把活着那一路做到 0.1 秒级；如果不可识别，也能彻底证明"锚点=巧合"，从此不再折腾这条路。

**加了什么（只加观测，不改任何判定逻辑）**：
- `GsiSample.changed`：把 `previously`/`added` 摊平成 `("prev:round.phase=freezetime",
  "add:round.bomb=true", …)`（最多 6 条，超出加 `…`；容器只记键名）。
- 日志 GSI 行末尾多一列 `Δ=…`；`安放(gsi+comp)` 行末尾多一列 `上包Δ=…`（心跳/无变化时是 `-`）。
- 自检 P0 新增 4 条：`chg=1` 的包必有变更键、心跳包必为空、键都带 `prev:`/`add:` 前缀、
  夹具里确实有改 `round.*` 的包。318 通过 / 0 失败。

**夹具里的先用结果（210 个真实包，观战那几局）**：6 次"安放跳变"逐个看，规律非常干净：

```
上1包  chg=1 phase=live   bomb=None      Δ=['prev:round', 'prev:round.phase=freezetime']
本 包  chg=1 phase=live   bomb=planted   Δ=['add:round', 'add:round.bomb=true']
```

- 揭示包的 `Δ` 里有 `add:round.bomb=true` —— **揭示包是可识别的** ✓
- 上一包的 `Δ` 是**回合刚进 live 的相位跳变**（`prev:round.phase=freezetime`）——
  也就是说锚点用的那包其实是"回合开始"触发的，不是"安放"触发的。
- ⚠️ **夹具里没有任何一包的 `Δ` 会在揭示之前提到 bomb** —— 即"安放会触发一包、只是内容还旧"
  这个假设在夹具里**找不到支持**。（注意夹具是观战抓的，而 Valve 2015 补丁的措辞是

### 23.3 改成"确认后才采用" + 进程环回重试（2026-09-17 实机日志之后）

**用户拍板**："可以做成确定不是误报再显示倒计时，从多少秒开始计时都行。"

⇒ 音频命中**不再立即建立 T0**，只挂成"待确认候选"；等 **GSI 揭示包**（Valve 自己的信号，
只是晚 0.03~2.6 秒）到达时，才用它把 T0 校准到精确安放时刻。
**没有确认就什么都不显示** ⇒ 误报彻底无害（连"撤回"都不再需要，屏幕上从没出现过东西）。
代价：面板出现时间 = GSI 揭示时刻（不再提前），换来的是数字准到 ±0.05 秒。

实机日志依据（`runtime/c4timer.log`，10 分钟）：音频安放 9 次、撤回 16 次、
GSI 安放 28 次；音频分数只有 0.72~0.75（中位 0.73），而离线真身 0.82~0.88 ⇒
这套环境下信号更弱且与误报重叠 ⇒ 不让音频决定"何时显示"是正确取舍。
另有**一次成功的实证**：`34565.06 安放(audio) 分数=0.75` → 40 秒后爆炸，
那一回合没有第二条 `gsi+comp` 安放 ⇒ 接线本身是对的。

**根因处理**：采集只在启动那一刻找一次 `cs2.exe`，找不到就永久退化成**系统环回**
（启动行 `audio: WASAPI system loopback`），别的程序的说话声混进来 ⇒ 人声模板误报。
现在改成：只要还在系统环回上，**每 20 秒重试一次进程环回**，游戏起来后会自动切过去

### 23.5 换特征：MFCC 有戏，调制谱没用（2026-09-17 晚，用户选①）

| 特征 | 真身（自相似度） | 误报 | 可分区间 | AUC |

| **MFCC（26 梅尔 → 13 倒谱）** | **0.277 / 0.396 / 0.396** | 0.072~0.277（中位 0.156） | 仅一点重叠 | **0.99** ✓✓ |
| 调制谱（包络 2~8Hz，音节率） | 0.213~0.286 | 0.155~0.325 | 无 | 0.31 ✗ |
| 谱平坦度 | 0.155~0.545 | 0.110~0.545 | 无 | 0.72 |

### 23.8 音频指纹（Shazam 式）**有效**：AUC 0.98（用户方案，2026-09-17 深夜）

用户指出关键点：**用 MFCC 等语音特征，本质是在判断"像不像人声"，而不是"是不是那一句
安放语音"** ⇒ 误判自然多。正确做法是**音频指纹**：只看时频图上的峰值点（星座图），
把峰值两两配成 `(f1_bin, f2_bin, Δt)` 哈希；真命中时命中点会在时间轴上排成**一条斜线**
（同一时间偏移），统计"最高时间偏移箱的命中数"即可；阈值用背景基线动态定。

**实现**（按用户给的参数：FFT 4096 / hop 1470，48kHz 下 85ms 窗、30.6ms 步长）：
每帧留最强 4 个局部极大峰 → 前方扇形区配对（Δt 1~40 帧、|Δf| ≤ 60 频点）→
哈希按 (f1/8, f2/8, Δt) 量化 → 命中按时间偏移分箱（±1 帧合并）取最大箱计数。

**评估**（样本 = 实战落盘的 真身 5 / 误报 21；留一法建参考表，绝不含被匹配者；
所有样本走同一套流程）：

| 类别 | 命中数（最大箱） |
|---|---|
| **真身（5）** | **24 / 27 / 40 / 52 / 52** |
| 误报（21） | 3,4,5,5,6,7,7,8,8,8,8,9,9,9,10,10,11,11,13,15,**30** |

- **AUC = 0.98**（对比：24 对数频带能量 ≈0.5、MFCC 0.63）
- 20/21 个误报 ≤ 15，真身最低 24 ⇒ **阈值 18~20 即可 5/5 召回**
- 唯一越界的那个（30 次命中、它的模板分 0.73 是所有误报里最高的）**很可能是标签错了**
  （真实安放那次 GSI 揭示包晚了 3.6 秒以上，或揭示包已在此候选之前出现过）——
  说明真实性能可能比这张表还好。

**结论**：音频这条路**重新变得可行**。下一步（按顺序）：

1. 把检测器换成指纹口径（不再用 24 频带能量）；用**干净的参考录音**建表
   （`sessions/*/audio.wav` 里对齐好的播报片段比实战落盘干净）；
2. 动态阈值：用"没有安放语音的正常对局音频"量背景命中率，阈值设在明显高于基线处
   （现在的数据：背景中位 8、上界 15~30）；
3. 保持"确认后才采用"（GSI 揭示包确认）作为上线第一步，达标后再谈"播报直接触发计时"。

**教训复用**：这次评估严格遵守"同一套流程给所有样本打分 + 留一法"，所以 AUC 0.98 可信
（前两次分别栽在数据泄漏和度量不可比上，见 23.4 / 23.6）。

### 23.9 onset 常数实机标定：0.8 -> 1.1 秒（2026-09-17 深夜）

用户对照**拆弹最后时限**逐局比对（保持"确认后才采用"不变），四局结果是：
两局偏早约 0.3 秒、一局偏晚、一局基本准。

偏早的来源是参考片段里那个写死的假设：参考从落盘第 3.0 秒切、假设播报落在片段起点后
0.8 秒（`ONSET_SEC`）。实际播报更靠后 ⇒ 算出的 T0 偏早 ⇒ 归零偏早。
把 `ONSET_SEC` 提到 **1.1**（整体后移 0.3 秒），并重建 5 个参考指纹。

该常数只影响"算出的时刻"，与命中数/误报数无关（分数是哈希命中数，不含 onset），
所以这次调整不动召回与误报（重建后仍是 4/5 召回、0/21 误报）。

残余抖动 ±0.3 秒级来自"每次落盘时播报在窗口里的位置略有不同"——要消掉它需要

### 23.10 参考指纹改成"按指纹对齐后切"（消抖动，2026-09-17 深夜）

用户反馈：标定完 onset 之后仍是"**有早有晚、每局都不一样**"。

原因定位：参考片段原来是**固定窗口**（从落盘第 3.0 秒切 2.5 秒），但每次落盘的时机
并不一致 —— 落盘发生在主循环处理命中时，而主循环每 0.4 秒才轮询一次，加上检测器自身
的滞后，于是"播报在窗口里的位置"每局差最多 0.4 秒 ⇒ 五个参考的锚点语义不一致 ⇒
每局偏得不一样。

修法：`tools/build_fingerprints.py` 现在用**指纹本身**把每段落盘对齐到第一段的坐标系
（`_align_start`：命中哈希的时间偏移给出对应关系），每个参考从**同一物理位置**开始切。
对齐不可信（命中 <6）时退回固定窗口，避免把参考切坏。

注意：这次改动会让**均值**略微漂移（对齐后以第一段为准），所以下一局如果整体偏早/偏晚，
用 `ONSET_SEC` 微调一次即可（它只影响算出的时刻，不影响命中与误报）。


### 23.11 抖动的真正源头修法：落盘窗口改成相对命中时刻（2026-09-17 深夜）

23.10 那个"按指纹对齐后切参考"的做法**实测没生效**：单段对单段的对齐命中数往往 <6，
于是全部退回固定窗口（重建后 5 个参考起点仍都是 3.00s）。这条不能算修好，已如实记录。

真正便宜的修法在**源头**：落盘原来取"处理命中那一刻的最后 6 秒"，而主循环每 0.4 秒才
轮询一次命中 ⇒ 播报在窗口里的位置每局差最多 0.4 秒。现在改成以**命中时刻 + 固定 1.5 秒
尾巴**结尾（`PlantVoiceDetector.pcm_window` + `AUDIO_DUMP_TAIL_SEC`），各局落盘里播报的
位置就一致了 ⇒ 由它生成的参考指纹锚点语义也一致。

注意：**已有的 5 个参考是旧落盘生成的**，仍带着旧抖动；要等用户再用新版本打一局、
用新落盘重建参考（`python tools\\build_fingerprints.py`）之后才彻底干净。

### 23.13 试过并否掉的两条路：谱白化、收窄频带（2026-09-18）

两条都是"看起来很合理"的直觉修法，实测都被数据否掉，记下来免得再走：

**① 谱白化**（每个频点除以自己的时间平滑本底，压掉宽带枪声、留窄带人声）：
动机是实战片段更吵（RMS 0.028~0.046 vs 参考 0.013）。
实测 4 段正样本 + 48 段负样本 ⇒ **负样本最高分从 8 涨到 108**，完全失去分辨力。
原因：哈希的频率量化只有 `F_BIN=8`（≈94Hz）一格，白化把峰值数量放大后，
大量虚假碰撞堆进**同一个时间偏移箱** ⇒ 分数虚高。

**② 收窄取峰频带**（200–6000Hz → 250–4000 / 300–3500 / 350–3000）：
直觉是低频爆炸声和 4kHz 以上的嘶声都是垃圾峰。实测更糟：
`250-4000` 下普通噪声片段飙到 **192 分**，而真身反而从 12 掉到 5。
同样是频率格变少 ⇒ 随机碰撞更容易撞进同一偏移箱。
⇒ **保持 200–6000Hz 不动。**

## 二十四、"为什么不那样做"（原 README 整节，2026-09-18 迁入）

README 现在只讲"是什么/怎么用/边界在哪"，取舍与否定方案的记录集中放在这里。

- **不做拆弹绿字**：需求变更后已移除。原因是音频这条路在实机环境里判别余量太薄
  （标定会话里真拆的分数连续 0.87~1.00，实机里却是稀疏尖峰），完整实验记录归档在
  `_archive/音频可行性实测.md`。
- **不复活"爆炸音效检测"那代音频链路**（2026-09-16 移除）：实机三轮里它每局只响 1~2 次候选，
  **全部落在 ±3 秒门控窗口之外**，从未真正确认过一次爆炸 —— 也就是说它从来没在真正需要它的
  时刻（GSI 断流）派上用场，却持续带来成本。另外那代采集还带两层不确定性：**设备路由**
  （回环录的是"系统默认播放设备"，CS2 输出被设成 HDMI/USB 耳机时就录到一路静音）与
  **回环可用性**（设备/驱动差异、独占模式、被切的输出）。
  ⚠️ 但**音频本身没有死**：2026-09-17 它以**指纹方案**（听安放播报，见第二十三节）回到产品，
  并且实机验证"每一局基本无偏差"。区别在于判据从"频带能量像不像人声"换成了
  "是不是**这一句**播报"，误报率差一个量级。
- **不用波形匹配滤波**：实测在本机素材上判别力中位只有 +0.027，异类最高分比多数同类还高。
- **不用官方音效当模板**：官方素材与游戏内混音的频带包络差异太大，判别力接近零。
- **不做 Game Bar 小组件**：需要 Visual Studio + Windows SDK（约 10GB），而它存在的唯一意义
  是覆盖独占全屏；本项目接受"全屏窗口化"。
- **不做炸弹滴声节奏识别**：离远了听不见（用户实机反馈）。
- **不用"端口是否被占用"做单实例判断**：端口是资源不是身份（曾经的采集工具也用 30077），
  用端口判断会把它误报成"程序已在运行"。改用命名互斥体。
- **不在 `defusing` 期间把 `bomb.countdown` 当炸弹时限**：实测那一刻它会从"到爆炸剩余"
  跳成"到拆弹成功剩余"（21.6 → 9.8）。1 代就栽在这里。所以现在 `defusing` 只被当作
  "红字照常走"的信号，不再参与任何倒计时换算。
- **不用"包间隔折半"去估算安放延迟**：这是**被后续实测推翻**的旧结论 ——
  当时算出的"L_p 与包间隔不相关（r = −0.26）"是拿**宽区间中值**算的，中值本身没有意义。
  用可靠点估计（`CALIB` 下界）重算得到 `L_p ≈ 间隔 + 0.11s`，17 局 + 夹具两局都对得上
  （残差 +0.102s、σ=0.007），这条关系现在**已经用上了**：它就是"锚点"路径
  （`state.ANCHOR_LEAD`）。详见第九节与第十六节。

**另一条通用教训**：本仓库的规矩是"**归档 > 删除**"，但归档必须**能用**才算数 ——
`_archive/audio_removed_20260916/` 原来写着"想复活照原路径拷回即可"，实测**不成立**
（缺 `c4timer/__init__.py`、且现役代码已经分岔），2026-09-18 已改成实话并给出从 git
历史取回文件的具体命令。

### 更正 1：那个"中文播报 13 分是虚假碰撞"的结论是错的

`zh_template.wav` / `*_zh.wav` 里装的其实是**同一句话**（只是被枪声盖住、或被片段截断的
弱命中）⇒ 它们得 13 分是**真身偏弱**，不是跨语言误报。影响两处：

1. `MIN_HITS=16` 是**偏保守**的估值（真实背景上限只有 7~10）。按上表，阈值降到 **10~12**
   有望在不增误报的前提下补回那次漏检 —— 但 4 参考 era 的背景只有 **3.7 分钟**，
   上尾还不够厚，**因此本次不动默认值**（已把阈值接成配置 `audio.min_hits`，随时可试）。
2. `tools/build_fingerprints.py` 的"误报筛查"基于同一个错误前提 ⇒ 它会把**好参考**丢掉
   （实测 `124452` 与 `124628` 就这么被筛掉的）。现在改成**显式开关**
   `--screen-negatives`（默认关闭），并在注释里写清了来龙去脉。

### 更正 2：5 个参考那套对真实播报几乎没响应

5 参考 era（09:23~11:46，**26 次安放**）**一个候选都没有**：安放窗口的分数只有 3~5，
而那时的 `need` 是 18~23。所以"多参考更稳"是错的 —— 参考要**少而准**
（现行 4 个，或干脆 2~3 个）。这也解释了为什么把参考从 5 个减到 1~4 个之后才开始有检测。

### 顺带两条工程建议（未实施，等有空）

1. **周期行应该记"滑动窗口峰值"而不是瞬时快照**：日志里出现过"快照 11 却出了 18 分的候选"、

2. **分数应按 `need` 归一化再打日志**：`need` 会随参考个数变（1 个→8，2~4 个→16，

## 二十六、试过并否掉：播放自带播报音频来免打局标定（2026-09-18）

**动机**：交付给别人时，标定音频要「先打一局」（程序每次安放后自动存 10 秒片段），
能不能改成自带一段标准播报音频、在对方机器上放一遍就完成标定？这样使用者步骤更少。

**做法**：从真实游戏片段里裁出那一句（3.2 秒，与现有参考同一切法）→ 用产品自己的
`LoopbackCapture` 录下「播放它的声音」两次 → 用第一遍建指纹参考 → 第二遍与真实片段做验证。

**第一次实验（只有真身、没有负样本）看起来成功** —— 四个真实游戏片段得 50 / 26 / 30 / 38，
全部远高于阈值 16。**但那是假象**：补上负样本对照后完全翻转：

| 目标 | 播放录音建的参考 | 现有参考（打一局那条路） |
|---|---|---|
| 真 121546 / 121853 / 124452 / 134531 | 38 / 17 / 13 / 11 | 42 / 55 / 36 / 32 |
| **负 live_114030（那一局没有安放）** | **3,067,200** | 0 |
| 负 live_114706 / live_121432 | 2,723,200 / 2,723,200 | 1 / 1 |
| 弱命中 zh_template | 28 | 13 |

**判据**：播放录音建出的参考有 **40989 个哈希**（真实参考只有 80~145）。哈希这么密 = 参考里
全是宽带噪声的峰 ⇒ **任何音频都能撞上几百万个命中** ⇒ 分数彻底失去分辨力。

**为什么**：真实链路里，「参考」和「实时音频」都是**同一套采集路径**录下来的游戏音频；
而「放一段 WAV 再用回环录回来」多经过一层系统混音 / 重采样 / 设备处理，把信号抹成了噪声底。
指纹靠的正是峰值位置的稳定性，这一层加工恰好破坏它。

**结论**：这条路**不可用**，不要再试。免打局标定的唯一可靠做法仍是「打一局 + `标定音频.bat`」。
（配套的临时工具 `tools/calibrate_from_clip.py` 与 `calib/announcement.wav` 已删除。）

**教训（与 23.4 / 23.6 同一类）**：**任何度量都必须带负对照**。第一次实验我只看了真身分数就
宣布成功，差点把一条无效路径交付出去；补上负样本后 3 秒就能看出它垮了。

## 二十七、使用者机器的完整验证：从"全新解压"到"实战生效"（2026-09-18）

背景：把 v0.1.7 精简包发给一位朋友（另一台机器、另一个 Steam 库、WeChat 传的文件、
**Python 3.14**）。他在自己电脑上从头走了一遍，过程中暴露出三个缺陷，全部落在同一条路上：
**全新机器、零参考指纹**。这条路在作者本机上永远走不到（本机一直有参考），所以三个都是
先由使用者撞上、再回头修的。

**三个缺陷与修法（按被发现顺序）**

| 版本 | 现象 | 根因 | 修法 |
|---|---|---|---|
| v0.1.8 | 控制台一直 `[跳过] 还没有安放片段`，整局一行 AUDIO 都没有 | `_start_audio` 在没有参考时直接 return，于是不启动采集；而标定素材（每次安放的 10 秒片段）正是采集攒的，自动标定又需要片段 => 死循环 | 没有参考也照样开采集，只录素材；`PlantVoiceDetector.feed` 在没有模板时也保留滚动 PCM 与样本计数（落盘片段的来源），`stream_time` 相应按样本数算 |
| v0.1.9 | 已有 1 个片段，却打印 `[X] 没有任何片段能与它互证` | 互证门槛（>=12 命中）本意是"多片段里挑最稳的一个"，却成了第一道门槛 | 只有 1 个片段时跳过互证直接建参考；另加 `MIN_REF_HASHES=20` 质量下限（裁到静音/纯噪声就不写文件，避免垃圾参考把后续自动标定锁死） |
| v0.1.11 | 4 个片段全部切好、互证也通过，写文件时 `FileNotFoundError: runtime\audio_templates\fp_01.npz` | 新机器上这个目录从没被创建过，而写 npz 前没有 mkdir（早先删临时工具时一并删掉了那句） | 写参考前 `OUT.mkdir(parents=True, exist_ok=True)` |

v0.1.10 还顺手把一次"两段对不上（只有 8 分）"从死胡同改成可执行诊断：打印每段片段的 RMS
与"正常应在 0.02 以上"的对照，并给出音量 / 输出设备 / 重试的具体建议。事后看，那次的 8 分
只是抽到了最差的一对：等材料攒到 4 段时，两两矩阵是 8~27，互证通过。

**修复的验证方式（这条比结论重要）**

三个缺陷本机都复现不了，所以每一次都是**把本地状态移走、人为造出"全新机器"的处境**再跑：

- 移走 `runtime/audio_templates` 全部参考 => 验"无参考也采集 / 单片段也能建 / 目录自动创建"
- 移走片段只留 1 个 => 验单片段路径
- 只留 2 段（含一段很吵的）=> 验对不上时的诊断输出

每一步跑完都把状态还原（参考与 32 个片段原样放回），并复核自检 359 通过 / 0 失败。

**最终结果（他那台机器上的实战日志）**

```

[102827.91s] 音频修正 T0 +1.87s（分数=27.00 模板=fp）
```

- **Python 3.14 上跑通**（程序、numpy、WASAPI 采集、指纹识别全部正常）。教程里的版本说明

## 二十八、自成长：累积统计与自动微调（2026-09-18，用户拍板"全自动，什么都不管"）

**目标**：使用者零操作，且打得越多越准。每局爆炸时的 `CALIB` 观测不再只是打一行日志，
而是被累积起来，自动微调**音频时间偏置**。

**四条设计约定**（都经用户确认）

1. **配置里永远只存手动值**（`audio.onset_bias_sec`）。自动修正量单独存在
   `runtime/calibration_stats.json`，运行时相加。手调值不会被覆盖，一眼能看出"程序贡献了多少"。
2. **清空 = 删掉那个统计文件**：自动量立刻归零，马上回到手动值；参考指纹不受影响。
3. **只为音频偏置自动调**。补偿值 `timers.plant_latency_compensation` 只在"锚点用不了"的
   少数局生效，而且是用户按实机反馈一手调出来的，自动去动它风险大于收益；`audio.min_hits`
   涉及"分数不可跨参考集比较"，留到统计系统跑稳之后单独做。这两个仍然只统计、只报告。
4. **按参考集分代**：观测里记着当时的参考集指纹（文件名 + 大小），参考一换旧观测作废
   （删掉 `fp_*.npz` 或者重建参考都会换代号）。

**门槛与限幅**（防止两三局就把常数带偏）

| 项 | 值 | 理由 |
|---|---|---|
| 最少有效观测 | 8 局 | 少于这个数，均值不可信 |
| 单局误差区间 | <= 1.2 秒 | 稀疏包局的区间宽到没有意义 |
| 均值标准误 | <= 0.08 秒 | 要求"不是靠运气凑出来的" |
| 单次调整 | <= 0.3 秒 | 别一步跳太远，留着下一局再修正 |
| 累计修正 | 夹在正负 0.8 秒内 | 防止一路跑偏 |

**符号约定**：误差 = 我们的归零 − 真实时限（正 = 偏晚）=> 偏置要减小，
所以自动量 = −clamp(平均误差)。

**缺局排除规则**（满足任一条就不进统计）

1. 那一局没有 `CALIB`（中途启动、没看到安放、没判到爆炸）
2. 误差区间宽于 1.2 秒
3. `T0来源` 是 `gsi-truth`（旁观位真值，本来就没有偏差可言）
4. 那一局音频没有生效（`CALIB` 的 `T0来源` 里不含 audio）—— 这类局不进音频偏置统计
5. 不是 CT 方（音频路径本身只在 CT 方启用，所以这一条由路径自动满足）

**实现**：`c4timer/tuning.py`（累积、门槛、限幅、摘要）+ `app.py` 三处接线
（把 `CALIB` 观测交给它、把 `offset()` 加进音频时间换算、启动时打一行摘要）。
启动摘要例如：`自成长统计：12 局有效观测，平均误差 +0.180s，标准误 0.060s，自动修正量 -0.18s`；
每次自动调整还会写一行 `TUNE` 到日志。

**验证**：自检新增 8 条断言（无观测时为 0、不足 8 局不生效、区间过宽不计入、方向为负、
单次与累计都受限、摘要可生成）；另做演习 —— 连续喂 8 局"偏晚 0.5 秒"，第 8 局触发
`+0.00s -> -0.30s`；再喂 30 局"偏晚 1.5 秒"，自动量被夹在 **-0.80s** 上限。
自检总数 359 -> 367 通过 / 0 失败。

**收尾时的两处修正**

1. 参考的身份**不用改数据结构**：`build_fingerprints.py` 早就把来源片段名写进了 npz 的
   `source` 字段（形如 `plant_20260917_212925.wav-aligned-len3.2s`），检测器报命中时带上它即可；
   日志里的 `模板=fp` 相应改成 `参考=<片段名>`。
2. 下滑判定的排序改用**全局递增序号**：原先按"每个参考最后命中时间"近似"最近的命中"，
   同一秒内的多次命中分不出先后 —— 演习里因此没判出下滑（先记 6 次 40 分建基线、再记 6 次
   12 分，结果"近期中位"仍取到 41.5）。改成每次命中带全局序号、按序号取最近 n 条后，
   同一演习判为下滑（近期 12.5 对基线 41.5）。这个缺陷的失效方向本来是安全的
   （判不出 = 不重标 = 参考不变差），但既然演习抓到了就修掉。

**还没做的（下一步）**

- **参考成长**：用户已同意做三件事 —— 片段攒够若干个就重建参考（保持最多 5 个）、
  重建时优先保留"实战里真正触发过的片段"、整体分数掉下来时（换语音包/设备/音量）自动重标。
  目前仍只在"一个参考都没有"时建一次。
- 把自成长摘要也打进 `体检.bat` 的输出（现在只在启动日志里）。

## 二十九、阵营门控取消：音频对两队都开（2026-09-19）

**起因**：复核说明书里"声音"这一节、准备给人讲清楚时，发现原来的说法
"T 方没有误差"站不住 —— 它只覆盖**自己下包**那一种情况。

**用户实机复核结论**：**T 方队友下包也有 ±1 秒误差。**（用户自己测的，不是推测。）

**机制上为什么原来会以为"T 方都准"**

- `docs/精度方案总览.md` 记的那条机制是"**自己下包**时，你自己的 `player` 块会变
  （C4 从背包里消失），那一包不受 Valve 那个延迟影响" —— 注意是**你自己的** `player` 块。
- 队友下包时变的是**队友**的块。而 `c4timer/gsi.py` 开头那条实测铁律写着：
  顶层 `bomb` / `phase_countdowns` / `allplayers` 是**观察者组件，只在本地玩家死亡并
  观战时下发** ⇒ 活着时根本收不到 `allplayers`，看不到队友背包里 C4 消失。
- 所以队友下包这一格，锚点一样退到常数补偿、一样 ±1 秒。

**改了什么**

1. `app._handle_audio_hit` 里的 `if self._team != "CT": return` **删掉**。
   剩下的门控只有"回合必须 live、GSI 还没揭示过安放"（三份录音里原始误报全部落在
   live 之外，这两条是数据逼出来的，与阵营无关）。
2. `state.AUDIO_KEEP_ANCHOR_SEC = 0.3` **新增**：音频与锚点本来就一致时**保留锚点**，
   返回 `kept` 而不是 `refined`。
   依据：锚点实际上只有两种状态 —— 认出"安放触发那一包"时准到 **0.02 秒级**；认不出时
   退到常数补偿、偏 0.3~2.4 秒。所以"音频与锚点差不到 0.3 秒"≈"锚点走的是准的那条路"，
   这时拿音频（±0.05~0.1 秒）去覆盖它只会更钝。延迟那条路偏 0.5 秒以上，拦不住。

**连带的两处口径**

- `kept` **不**把 `T0来源` 标成 audio：T0 不是音频定的，标了会让时间侧自成长把锚点的
  误差当成音频偏置去学。`docs/自成长设计.md` 的"缺局排除五条"同步改了第 5 条。
- `kept` **仍然**计入参考的实战成绩（`refstats.record`）：那是一条确认过的真命中，
  对"哪个参考值得留"是有用证据。

**验证状态**

- 自检 475 项全绿。
- **实机已验（2026-09-19 深夜，用户原话："实际对局很完美，基本无误差"）。**
  把 2.6 MB 日志里 89 条 `CALIB` 的**误差下界**按"音频有没有生效"分组统计 ——
  看下界而不是区间中点：区间宽度由 GSI 报文间隔决定，与我们的精度无关，
  下界（"确定不早于这个数"）才反映真实偏差。

  | 分组 | 局数 | 下界最小 | 下界中位 | 下界最大 | \|下界\|中位 | 落在 ±0.3 内 |
  |---|---|---|---|---|---|---|
  | 音频生效 | 19 | −0.24 | +0.01 | +0.81 | **0.02 秒** | **18/19** |
  | 没生效 | 70 | −0.88 | +0.02 | +1.98 | **0.54 秒** | 24/70 |

  ⇒ 中位绝对误差 **0.54 秒 → 0.02 秒**。而且两条新逻辑在同一段日志里各自有样本：
  * `kept`：`00:04:31  本局误差 [+0.02, +0.89]s  T0来源=gsi+comp`
    —— 锚点没被动，误差 +0.02，正是"保住自己下包那 0.02 秒"要的效果。
  * `refined`：`00:06:10  本局误差 [-0.01, +3.50]s  T0来源=gsi+comp+audio`
    —— 音频修正后 -0.01。
